TASK-010: why the window's start stalled in the private test session on 2026-10-04, recorded 2026-10-05T06:50:44+02:00.

What was seen on 2026-10-04 from about 20:03: started in the end-to-end test's private session, the window stayed on its
loading screen. Theia had started its contributions and then waited for one drawn frame before attaching its workbench;
requestAnimationFrame never fired, although the page reported itself visible. Asking the page for a screenshot over the
DevTools protocol made it draw a frame, and the start went on. The same installation had started normally at 19:20 and
19:50, and it started normally again on 2026-10-05 after the machine was restarted.

The cause: the login session was marked as locked. A nested KWin compositor follows that mark (logind's LockedHint of
the user's session): it starts its own lock screen, which covers every window, and it draws no client window while
locked. The mark is set when the real screen is locked, and also when any nested compositor locks itself. Nothing of
TASK-010's changes is involved, and a window on a real, unlocked screen is drawn as usual.

3. A third observation on 2026-10-05: a private session started at 07:35:01 and left without input. At 07:41:40 its
   compositor had a lock screen of its own (one lock-screen process below it), and LockedHint of the login session was
   yes. The private session was then stopped. At 07:42 no lock-screen process ran on the machine at all, so the real
   screen was not locked, and LockedHint was still yes. So a private session that gets no input for some minutes locks
   itself and marks the user's whole login session as locked, and the mark stays when the private session ends, until
   the real screen is next locked and unlocked. The task did not change the mark. This is what the session that ended
   at 19:31:44 on 2026-10-04 most likely did. Which of the two set the mark later that evening, a private session or a
   lock of the real screen, was not established.

4. What the task did about it. The end-to-end test asks the page for one pixel at each probe (its function `shown`),
   which draws a frame, so the test does not depend on the mark: it passed its checks on 2026-10-04 at 20:14 with the
   session marked as locked, and on 2026-10-05 without the mark. One run of the test takes about a minute, far less
   than a compositor needs to lock itself. The task's own debugging sessions are now closed within four minutes.
   Nothing was changed about screen locking, in the test session or anywhere else.
